# SkyScan — Phase 0 Audit Report

**Scope:** Static read-only audit per `Phase 0.md`. No code was changed. No build/test was run — every claim about compilation or runtime behavior is flagged unverified where applicable.
**Method note:** The repo already contains prior audit/planning docs (`SkyScan_Architecture_Audit.md`, `SkyScan_Current_Issues_Fix_Plan.md`, `SkyScan_Future_Roadmap_Plan.md`) from earlier sessions, and git history shows substantial refactor work landed after those docs were written. Those docs were used only as a hypothesis list — every item below was re-verified against the current file contents, not copied. Several previously-documented issues turned out to be already fixed; this report states current reality.

---

## 6.1 Summary

The codebase is in noticeably better shape than the brief's "Context Snapshot" assumes: the User/Identity domain-purity fix is done cleanly (plain `User` entity, `AuthResult` value object, `ApplicationUser`/`IdentityResultExtensions` correctly isolated to Infrastructure), `IBookingRepository` exists, and `FlightController`/`BookingController` no longer touch `SkyScanDbContext` directly. The DTO-in-Core deviation the brief describes is also already resolved — `SkyScan.Core/DTOs` is empty, and real DTOs live correctly in `SkyScan.Application/DTOs`. That said, real problems remain: `AccountController` still injects `SkyScanDbContext` directly for a 5-level `Include` chain, CQRS is 100% unimplemented (empty `Commands`/`Queries` folders, no MediatR, a fully-written `FlightSearchRequestValidator` that is never registered or invoked), the Google Calendar integration is implemented entirely as raw `HttpClient` OAuth/API calls inside `BookingController` with no Infrastructure abstraction, and the test project still targets `.NET 10` against a `.NET 8` solution. Test coverage is effectively two files covering happy-path scenarios only. Nothing found here looks like it would outright block a build (the `.NET 10` mismatch is the only candidate, and even that likely just requires an SDK capable of both — flagged, not asserted, per the ground rules). The biggest risk to the evaluation is architectural inconsistency (partial fixes coexisting with un-fixed instances of the same problem) rather than outright breakage.

## 6.3 Evaluation Criteria Cross-Check

**Google Sign-In (OAuth).** Implemented and functionally complete: `AccountController.GoogleLogin`/`ExternalLoginCallback` correctly use `SignInManager.ConfigureExternalAuthenticationProperties`/`GetExternalLoginInfoAsync`, auto-provision a new `User`/`ApplicationUser` on first login with `EmailConfirmed = true` (reasonable, since Google already verified the email), and link the external login via `UserManager.AddLoginAsync`. The random-password-on-Google-signup pattern (`Guid.NewGuid() + "Aa1!"`) is a common, acceptable technique for Identity-backed external-only accounts. No structural problems found. **Verdict: Solid.**

**User Management.** Registration, login, email confirmation, forgot/reset password, 2FA (authenticator-based) setup/verify/disable, and password change are all present and functional. The gap is architectural consistency, not functionality: some operations go through `IUserRepository` (the intended Core-facing abstraction) while others (`ChangePassword`, 2FA enable/disable, external-login callback) call `UserManager`/`SignInManager` directly from the controller (Finding #17). Account-lifecycle completeness is also short two items graders commonly check for: account deletion and email change (Finding #29) — both absent. **Verdict: Needs Work.**

**External API Integrations (Amadeus, Nominatim, Currency, SMTP).** All four have dedicated, interface-driven Infrastructure services, which is the right shape. Amadeus is the most fleshed out (native round-trip via real Amadeus itinerary segments, DB-backed airline/airport resolution, in-request airline-name caching) but has real gaps: no Polly/resilience policy despite the project's own instructions calling for one, `Console.WriteLine` instead of `ILogger`, a silent `DateTime.Now` fallback that can fabricate flight times, and a query method that silently writes to the database (Findings #10, #12, #13, #14). Nominatim and Currency are simpler and comparatively clean (Currency has a nice hardcoded-fallback-on-failure pattern). SMTP is minimal but correct. **Verdict: Needs Work** (the pattern is right, the hardening called for in the project's own instructions — Polly specifically — is not done).

**Clean Architecture correctness, Presentation as MVC.** Genuinely mixed. On the positive side: the dependency graph is now correctly directed (verified — Core has no project references and no Infrastructure/Application types leak in; Application depends only on Core; Infrastructure depends on Core+Application; Presentation depends on both), the User/Identity domain-purity fix is done properly, and most controllers route through repositories rather than raw EF. On the negative side: CQRS is completely absent despite being an explicit architectural mandate (empty `Commands`/`Queries` folders, no MediatR, a fully-built validator that's never invoked), `AccountController.Profile()` still bypasses the repository layer entirely, and the Google Calendar integration is implemented as raw infrastructure-grade code (HTTP calls, OAuth token handling, JSON payload construction) sitting directly inside a controller — the single clearest violation of "Presentation... no business or data access logic" in the codebase. **Verdict: Needs Work.**

## 6.4 Account Deletion — Proposed Design

*(Design only — nothing here has been implemented.)*

**Confirmed missing today:** no delete-account action, no email-change action, no data-export/download action. Password change exists and is correctly wired (`AccountController.ChangePassword` → `UserManager.ChangePasswordAsync`).

**Soft-delete vs. hard-delete — recommendation: soft-delete, with a hard-delete purge job behind it.**
Reasoning: `Booking` records are the closest thing this system has to a transactional/financial record (they represent a completed redirect-to-book action with a timestamp), and immediately hard-deleting a user plus cascading into their bookings destroys data that may matter for dispute resolution, analytics, or — if SkyScan ever needs to demonstrate GDPR "right to erasure" compliance properly — a documented deletion trail. A soft-delete (`IsDeleted` + `DeletedAtUtc` on `ApplicationUser`, sign-out forced immediately, login blocked thereafter) combined with a scheduled hard-purge after a grace period (e.g. 30 days) gives you both: immediate "my account is gone" behavior for the user, and a real erasure event later that can be logged for compliance purposes without permanently destroying data the instant someone clicks a button (which is also a foot-gun against accidental/malicious deletion requests).

**What cascades:**
- `Booking` — tied to `UserId`. Soft-delete: leave rows in place (they reference a now-deleted user); hard-purge: delete outright, no dependents.
- `PriceAlert` — tied to `UserId`. Should be hard-deleted (or at least disabled) immediately on soft-delete, not just at purge time — there's no reason to keep running the 6-hour price-check worker against a deactivated account, and the worker doesn't currently check any "is this user still active" flag (Finding-adjacent: worth folding into whatever soft-delete flag gets added).
- `Search` — tied to `UserId`, used for trending-route analytics. Reasonable to anonymize (null out `UserId`, keep the row for aggregate trending stats) rather than delete outright — this is exactly the kind of aggregate-vs-personal-data distinction GDPR erasure guidance draws.
- `ApplicationUser` (Identity tables: `AspNetUsers`, `AspNetUserLogins`, `AspNetUserTokens`, etc.) — soft-delete flag on `AspNetUsers`; external login links (Google) should be revoked/removed immediately so the same Google account can't silently re-authenticate into a "deleted" account.

**Layer placement:**
- `IUserRepository` gets a new `Task<AuthResult> DeleteAccountAsync(Guid userId)` — this is the same pattern already established for every other Identity-touching operation (bridges to `UserManager` in `UserRepository`, returns `AuthResult` like everything else).
- The cascade orchestration (touching `PriceAlert`, `Search`, `Booking` across multiple repositories) is a multi-repository operation — it does **not** belong inside `IUserRepository` itself (that would make the user repository reach into unrelated aggregates). This is exactly the kind of orchestration the brief's own CQRS mandate is for: a `DeleteAccountCommand`/handler in Application that calls `IUserRepository.DeleteAccountAsync` plus `IPriceAlertRepository`/`ISearchRepository`/`IBookingRepository` cleanup methods, all wrapped in one transaction. If CQRS isn't in place yet (it currently isn't — Finding #2), a plain Application-layer `IAccountDeletionService` with the same responsibility is an acceptable interim shape, provided it's understood as a stepping-stone.
- The controller (`AccountController.DeleteAccount`) should do nothing but: confirm the requester is deleting their own account, require re-authentication or password confirmation (see security note below), call the Application-layer command/service, sign the user out, redirect home.

**Auth/security and GDPR-style considerations:**
- Require re-entering the current password (or a fresh sign-in) immediately before deletion — this is a destructive, irreversible-from-the-user's-perspective action and shouldn't be a single accidental click while a session is merely still logged in on a shared device.
- `[ValidateAntiForgeryToken]` + `[Authorize]`, consistent with every other state-changing action in `AccountController` today.
- Rate-limit the endpoint (the project already has a `BookingPolicy` rate limiter pattern in `Program.cs` — reuse the same approach) to prevent abuse.
- Send a confirmation email on completion (SkyScan already has `IEmailService`/`SmtpEmailService` wired for this exact kind of transactional email) — both as a UX courtesy and as a paper trail that the deletion request was processed.
- If SkyScan wants to make a real GDPR claim (reasonable for a project that will be evaluated professionally, even if not legally required at this scale), document the retention window explicitly (e.g. "deleted accounts are hard-purged after 30 days") rather than leaving it implicit — auditors and graders both look for a stated policy, not just code that happens to do the right thing.
- Data export/download (also missing, per Finding #29) is a natural companion feature to build alongside deletion — the same "here's everything we hold on you" query (`Bookings` + `PriceAlerts` + `Searches` by `UserId`) that deletion needs to enumerate in order to cascade correctly can be reused to serve a JSON/CSV export before the account is removed.

### Test coverage gap map (feature area → what's missing → why it matters)

- **Flight Search** (`FlightController.Search/Results`, `AmadeusFlightService`, `FlightFilteringService`) — zero tests today. This is the single most-used code path in the product; `FlightFilteringService`'s pure-DTO filtering logic (Finding-adjacent: it has zero external dependencies, making it the easiest thing in the whole solution to unit test) has no coverage despite being trivially testable. Protects against silent regressions in price/stop/airline filtering and sort order.
- **Booking** (`BookingController.Book/MyBookings`, guest-cookie logic) — zero tests. This path handles both authenticated and guest flows, materializes flights on demand, and creates price alerts as a side effect of booking — exactly the kind of multi-branch logic that regresses silently without tests. Guest-cookie serialization/deserialization (`GetGuestBookingsFromCookie`) is also untested and swallows exceptions silently (`catch { return new List<...>() }`), which a test would catch if the JSON shape ever drifts.
- **User Accounts** — partially covered (5 happy/invalid-model-state tests in `AccountControllerTests`). Missing: 2FA setup/verify/disable, Google external-login callback (new-account-creation branch specifically), `ChangePassword`, `RefreshCookie`, and every failure path (wrong password, locked-out account, expired token) beyond the ones already covered. Auth code failing silently in the *wrong* direction (e.g., letting an invalid 2FA code through) is the highest-consequence class of bug in the app; it currently has the least verification for its risk level.
- **Price Alerts** (`PriceAlertCheckWorker`, `IPriceAlertRepository`) — zero tests. This is the one fully-async, unattended feature in the app (runs every 6 hours with no human in the loop) — if `EvaluateAlertAsync`'s price-comparison or email-trigger logic regresses, nothing will surface it until a user notices they never got an alert. Highest-value place to add tests precisely because it's the least observable in normal use.
- **Location Lookup** (`ILocationLookupService`/Amadeus, `NominatimGeocodingService`, `LocationSearchService`) — zero tests. `LocationSearchService`'s in-memory ranking logic (airport-type → rank → sort) is pure and easily testable; protects the "did you mean this city" UX from silently regressing.
- **Currency** (`CurrencyConversionService`) — zero tests, despite having the clearest test seams in the codebase (cache-hit vs cache-miss vs API-failure-fallback are three distinct, easily-mockable branches). Protects the fallback-to-hardcoded-rates behavior specifically, since a broken fallback would only surface when the real API is already down — the worst time to discover a second failure.
- **Internationalization** (`LanguageService`, Arabic name fallbacks scattered through `FlightController`/`AirportRepository`) — zero tests. Low complexity, but the `isAr && !string.IsNullOrEmpty(x.NameAr) ? x.NameAr : x.Name` fallback pattern is repeated in multiple places; a shared helper plus a test for the "Arabic name missing" branch would both reduce duplication and lock in the fallback behavior.

Not flagging the amenities one as a defect (it's a documented, reasonable approximation), but worth deciding as a pair whether "clearly fake, only for demo polish" data like this needs a UI disclaimer before evaluation.

## Ambiguities requiring your decision before any Phase 1 work

1. **CQRS retrofit scope.** Introduce MediatR as a full retrofit across all controllers, or a single pilot slice first? The brief's own instructions treat CQRS as required; the codebase today has zero of it. Doing it properly touches nearly every controller action.
2. **Trending-route `MinPrice` fabrication (Finding #9).** Leave as a labeled placeholder, or wire to something real (e.g., last cached search price for that route) before evaluation?
3. **Cookie `SameSite` policy (Finding #16).** `Strict` is more correct but risks breaking the Google OAuth external-login redirect (which crosses origins to accounts.google.com and back) — needs a decision informed by testing that specific flow, which requires running the app.
4. **Identity access pattern consistency (Finding #17).** Should every `AccountController` action route through `IUserRepository` for consistency, even the ones (`ChangePassword`, 2FA enable/disable) that currently call `UserManager`/`SignInManager` directly? This is a genuine two-reasonable-answers call: full consistency vs. not over-abstracting operations that are already thin one-liners against `UserManager`.
